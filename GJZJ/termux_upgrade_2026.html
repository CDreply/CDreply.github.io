01PHP 是什么

如果你只写过 HTML，可以这样理解：

一句话版本 PHP 是一种「跑在服务器上的编程语言」，专门用来现做网页。你在地址栏敲一个网址，服务器上的 PHP 就开始干活——查数据库、拼 HTML、算好结果，再把整页塞给你的浏览器。

它和前端语言的区别

HTML / CSS / JavaScriptPHP
在哪运行你的浏览器里服务器上（你看不到它的代码）
你能看到源码吗能（右键查看源代码）不能，只收到它算完的结果
典型用途页面长相、交互登录、发帖、上传、查数据

所以你浏览一个 PHP 网站时，浏览器和服务器之间是这样的：

浏览器  ──请求──▶  服务器（PHP 在这里执行）  ──HTML──▶  浏览器显示
关键点：漏洞在「服务器那一端」 浏览器里的一切都是安全的——你只是收到了结果。出问题时，出事的是那台服务器：别人拿到了它的控制权。

PHP 有两种跑法，安全性差别很大

方式怎么工作这次漏洞下的风险
mod_phpPHP 被编译成一个模块，直接塞进 Apache 里，每个请求都由 Apache 自己解释最高 请求在业务代码执行之前就被打穿，安全插件、维护模式全都看不见
php-fpmPHP 是一个独立后台进程，nginx 收到请求后转交给它处理高 至少中间隔了一层，可以做网络层拦截

怎么知道自己用的是哪种？在服务器上跑：

# 看有没有 php-fpm 进程在跑
pgrep -a php-fpm

# 看 Apache 有没有加载 libphp 模块
ls /usr/lib/apache2/modules/libphp* 2>/dev/null

前者有输出 = php-fpm；后者有输出 = mod_php。

顺便说个数字

全球大约 七成 的网站用 PHP。WordPress（全球四成网站）、Wikipedia，以及大量论坛、商城、企业站都建立在它上面。所以 PHP 一出底层漏洞，波及面是全行业级别的。

02这次漏洞影响什么

编号类型可能后果
CVE-2026-109618Use-After-Free（释放后使用）未授权远程代码执行
严重度 CVSS 4.0 = 9.2
CVE-2026-109619内存泄露

「Use-After-Free」到底是什么意思

打个比方：程序向系统借了一块内存放数据，用完归还了。正常情况这块内存不该再碰。但如果程序有个逻辑错误，归还之后还在用这块地址——而系统已经把它分给别人了——那它读到的就是别人的数据，写进去就是改别人的数据。

攻击者要做的，就是精心安排“别人”是谁。安排得当，就能让程序替他执行一段他自己写的代码。这就是 RCE（Remote Code Execution，远程代码执行）——一整台服务器的控制权。

触发条件有多低

项目情况
要登录吗不用
要用户点击吗不用
要你的代码有 bug 吗不用，漏洞在 PHP 引擎本身
怎么触发发一个特制的 multipart/form-data 请求（就是网页上传文件用的那种格式）
意味着什么 哪怕你的网站上只跑着一句 Hello World，只要它由受影响版本的 PHP 处理请求，就同样可被打。业务代码写得再干净也不顶用——底座漏了。

影响范围与修复版本

版本
受影响≤ 8.5.11 / 8.4.26 / 8.3.35 / 8.2.34（再往前的旧分支基本全中）
已修复8.5.12 / 8.4.27 / 8.3.36 / 8.2.35
8.1 及更早分支 官方只提供了「最小化源码回溯补丁」，需要自己编译。而 8.1 整条线在 2025-12-31 已 EOL——也就是说近一年积累的所有 PHP 漏洞都没有官方修复。这类环境建议直接换容器或换技术栈，不要指望打补丁。

为什么 phpMyAdmin 这类工具特别危险

两个原因叠加：

  1. 它的正常运行就会踩中利用路径。phpMyAdmin 启动就要 session_start()、解析序列化数据，正好是 109618 的已知触发点。
  2. 它的进程内存里躺着数据库账号密码。打穿一个管理工具，等于把整个数据库的连接凭证一起交出去。

三分钟自查

# 1. 看 PHP 版本（要看完整的第一行，含构建日期）
php -v | head -1

# 2. Debian/Ubuntu 系：安全补丁会加 debXXuX 后缀，版本号本身不变
dpkg -l | grep -E 'php[0-9]|libapache2-mod-php'

# 3. 容器里装的（有 docker 的话）
docker ps
Debian 系的坑：版本号没变不等于没修 发行版的安全更新走 backport，不改上游版本号，只在包版本后面加后缀（如 8.2.30-1~deb12u2）。所以 php -v 显示 8.2.30 只证明“上游没发新版”，不证明“你的系统没修”。必须看 dpkg -l 的后缀。

03为什么不能分批升

这是整件事最关键的一个认知。看 pkg 命令的源码（termux-tools/scripts/pkg.in）：

// pkg 脚本里 upgrade 分支的实现
up|upg*) select_mirror; apt update; apt full-upgrade "$@" ;;

这句在 v1.32 到 v1.46 之间完全没变。也就是说 pkg upgrade 一直就是 apt full-upgrade 的包装，不是“更激进的替代品”。

两种命令的实测差异

命令实测结果原因
apt-get upgrade98 升 + 28 个被 kept back只换版本，不允许安装新包。新版 termux-tools 依赖一个三年前不存在的包（termux-core），整条依赖链被挡住
apt-get full-upgrade126 升 + 31 新装 + 3 删 + 0 扣留允许安装新包，依赖一次配齐
半升级长什么样 那 98 升里包含 libicu 72 → 78，它的 SONAME 从 libicuuc.so.72 换成了 .78（SONAME 相当于库的“身份证号”，所有链接它的程序都按这个号找文件）。

而被扣留的 28 个里包含 php、nodejs、glib——它们全都链接着旧号的 ICU。

结果：库换了新号，程序还在按旧号找，启动立刻报错：
CANNOT LINK EXECUTABLE ... libicuuc.so.72 not found

量化特征：Need to get 只有几十 MB。完整升级应是一两百 MB——数字异常小，就是半升级的信号。

三个数字验收

# -s 是 simulate，只算不装；把结果存文件，避免用 tail 切掉摘要
apt-get -s full-upgrade > ~/plan.txt 2>&1

# 摘要行：升了多少 / 要下多少 / 有没有被扣
grep -E 'upgraded,|Need to get|not upgraded' ~/plan.txt

# 数一下要安装的条目数
grep -c '^Inst ' ~/plan.txt

# 列出会被删除的包（一定要看！）
grep '^Remv ' ~/plan.txt
看什么应为异常时
not upgraded0非 0 说明还有包被扣，别升
Inst 行数接近待升级总数远小于 → 依赖没解开
Remv 列表只含包结构重构的旧包出现 bash / coreutils / dpkg / apt 立刻停手
取证写法很讲究 别用 | tail -40 看 apt 的计划——摘要（多少升、多少删、下多少）在输出开头，明细在后，tail 恰好把最关键的行切掉。一律先 > 文件 存盘再 grep。
看到 autoremove 候选，千万别动手 升级前 apt 会列出一堆“不再需要”的包。别信——那是因为依赖它们的包还没升级完。本次候选里有 libgd、unbound、fontconfig、openssl-1.1，删了等于拆掉 PHP 图像处理和 DNS 的基座。全部验证通过之前，不碰 apt autoremove。

05php-fpm 起不来

现象

ERROR: failed to include more than 5 files recursively
ERROR: Unable to include .../php-fpm.d/www.conf from .../php-fpm.d/www.conf at line 143
ERROR: FPM initialization failed

翻译成人话：一个配置文件在 include 它自己，递归到第五层被掐断。

第一层误判（我踩过）

看到“从自己 include 自己”，很自然会想“末行多了条 include 吧”。确实，池配置文件末尾写着：

include=/data/data/com.termux/files/usr/etc/php-fpm.d/*.conf

这行本该只出现在主配置 php-fpm.conf 末尾，职责是把 php-fpm.d/ 下的所有池配置加载进来。删掉它之后，报错变成：

ERROR: No pool defined. at least one pool section must be specified in config file

真正的根因

整个 www.conf 是 php-fpm.conf 的副本 对比文件大小就露馅：出问题的 www.conf 只有 143 行 / 5.4KB，而包内自带的 www.conf.default 是 489 行 / 22KB。

更直接的判据：那 143 行里根本没有 [www] 段，全是 global 段的注释和配置——也就是 php-fpm.conf 该有的内容。

所以不是“多一行”，是整个文件被写错了。

修法

# 1. 先看有没有池段（^\[ 表示以 [ 开头的行）
grep -n '^\[' $PREFIX/etc/php-fpm.d/www.conf
# 输出为空 → 确认没有池段，需要重建

# 2. 用包内自带的完整默认配置覆盖
cp $PREFIX/etc/php-fpm.d/www.conf.default $PREFIX/etc/php-fpm.d/www.conf

# 3. 再看一次，应出现 [www]
grep -n '^\[' $PREFIX/etc/php-fpm.d/www.conf

# 4. 检查语法
php-fpm -t
# 应显示 test is successful

顺带的小坑：行数对不上

wc -l php-fpm.conf 报 142 行，报错却说 at line 143——因为末行没换行符时 wc -l 不计数。行数差 1 不代表文件坏了。

listen 必须和 nginx 对齐

新版默认监听 unix socket，而 nginx 可能写着 fastcgi_pass 127.0.0.1:9000。两边不一致 = 502。

# 看 fpm 监听什么
grep -E '^listen' $PREFIX/etc/php-fpm.d/www.conf

# 看 nginx 往哪转
grep -rn 'fastcgi_pass' $PREFIX/etc/nginx/

# 方案 A：改 fpm 用 TCP（只动一处）
sed -i 's#^listen = .*#listen = 127.0.0.1:9000#' $PREFIX/etc/php-fpm.d/www.conf

# 方案 B：改 nginx 用 socket（在 nginx.conf 里写）
# fastcgi_pass unix:/data/data/com.termux/files/usr/var/run/php-fpm.sock;

php-fpm -t && sv restart php-fpm
为什么本文推荐 TCP unix socket 还牵扯权限：user = nobody 在非 root 环境下会被忽略（启动时打一条 NOTICE），实际 worker 以当前用户身份运行，socket 属主也是它。多一层变量。回环 TCP 在手机上几乎没有可感知的性能损失。

06nginx 双实例

现象

pgrep -a nginx
26136 nginx: master process nginx
27228 nginx -p /data/data/com.termux/files/home/.nginx -g daemon off;

两个主进程抢一个端口。一个占着，一个 bind 失败——但都留在进程表里，看起来“都活着”。sv status 显示的 pid 和 netstat 显示的对不上，就是信号。

我犯的错：一条命令杀掉两种进程

pkill -9 -f nginx 把监督进程也杀了 -f 匹配完整命令行。而 runit 的监督进程，命令行是 runsv nginx——里面正好含 “nginx”。

结果：nginx 死了，看守 nginx 的进程也死了。再敲 sv up nginx 会得到：
fail: nginx: runsv not running

sv 是跟监督进程说话的。监工被杀了，sv 就成了对空气喊话。

正确做法

目的正确写法不要用
停服务sv down nginx（runsv 自己会杀干净）pkill -f nginx
杀残留进程pkill -x nginx（只匹配进程名等于 nginx）pkill -9 -f nginx
重启sv restart nginxkill <pid>

误杀之后怎么救

# 1. 重新拉起 runsvdir（服务监督总进程）
source $PREFIX/etc/profile.d/start-services.sh

# 2. 确认各服务的监督进程回来了
pgrep -a runsv

# 3. 清掉 down 文件并启动 nginx
sv up nginx

# 4. 确认状态
sv status nginx
为什么 sv up 不能省 sv down 会在服务目录里留一个 down 文件。runsvdir 恢复后，runsv 看到这个文件会认为“是用户手动停的”，不会自动拉起。sv up 的作用就是删掉它。

另外 sv status 尾部那个 normally down 不用管——服务目录没有 down 文件时 runit 就这么显示，服务其实在跑。

07站点文件被覆盖

升级 nginx 包会重装 $PREFIX/share/nginx/html/index.html 如果你把站点直接放在这个默认 web 根下，升级后首页会变回 “Welcome to nginx!”。其它资源（css/js/子目录）都在，只有 index.html 被覆盖。

恢复：

# 把生成好的静态文件拷回站点根
cp -rf ~/your-site-public/* $PREFIX/share/nginx/html/

# 确认首页回来了
curl -s http://127.0.0.1:8080/ | head -5

长期方案：把站点搬出包管理目录

# 1. 建一个自己的目录
mkdir -p ~/www

# 2. 把站点文件搬过去
mv $PREFIX/share/nginx/html/* ~/www/ 2>/dev/null

# 3. nginx.conf 里改成绝对路径
# root /data/data/com.termux/files/home/www;
相对路径的陷阱 root html; 是相对路径，实际解析取决于 nginx 启动时的 -p（prefix 前缀）参数。加上 -p 之后，同一个配置会指向完全不同的目录。排查站点 404 时，第一件事就是看进程的 -p 是什么。

08Python 包失效

Python 从 3.11 升到 3.14 之后，所有 pip 装过的命令行工具都会报：

ModuleNotFoundError: No module named 'xxx'

原因很简单：第三方包装在带版本号的目录里（$PREFIX/lib/python3.11/site-packages），解释器一换代，旧目录就不再被读取。

# 看看现在有哪些包
pip list

# 重新装回你要用的那个
pip install -U <包名>

# 若提示 externally-managed-environment
pip install -U <包名> --break-system-packages
Node 同理 全局 npm 包装在 $PREFIX/lib/node_modules，Node 大版本升级后命令行工具会失效，需要 npm install -g <包名> 重装。

09踩坑清单

#坑教训
1apt-get upgrade 造出半升级apt upgrade 不允许装新包，依赖链整条被扣。pkg upgrade 内部就是 full-upgrade，别拆

5pkill -f 杀了 runit 监督进程用 sv down 或 pkill -x

12备份与恢复

成对使用：下面「备份」和「恢复」紧挨着放，方便对照。两者是两套独立命令，不要混着敲——尤其 tar -c（打包）和 tar -x（解压）只差一个字母，敲错了会覆盖数据。

12.1 备份（升级前先做这个）

先分清两种东西的性价比：

备份对象可再生吗优先级
业务数据：站点文件、上传的附件、配置（$HOME 下的东西）不可再生最高
运行环境：所有已装的包（$PREFIX）可再生，重装即可省重装时间，也值得做
# ① 建备份目录（放共享存储 /sdcard，不要放 $HOME，卸载 app 会一起删）
mkdir -p ~/storage/shared/backup

# ② 备份业务数据
#    -c 创建归档 / -z gzip 压缩 / -f 指定文件名
#    $(date +%F) 自动插入当天日期，如 2026-10-23
#    -C 先切换到指定目录，再打包后面的 <数据目录>
tar -czf ~/storage/shared/backup/data-$(date +%F).tar.gz \
  -C $HOME <你的数据目录>

# ③ 备份整个运行环境（$PREFIX）
#    --exclude 排除缓存和临时文件，能省几百 MB
#    -C /data/data/com.termux/files 先切到上级，再打包 usr 目录
tar -czf ~/storage/shared/backup/prefix-$(date +%F).tar.gz \
  --exclude='usr/var/cache/apt/archives/*' \
  --exclude='usr/tmp/*' \
  -C /data/data/com.termux/files usr

# ④ 记录已安装包清单（方便日后对照或重建）
dpkg --get-selections > ~/storage/shared/backup/selections-$(date +%F).txt

# ⑤ 检查结果：能看到文件大小就说明成功了
ls -lh ~/storage/shared/backup/

# ⑥ 确认剩余空间（快照通常 200MB~1GB）
df -h /data | tail -1

# ⑦ 验证压缩包能正常读取（强烈建议做，别等到要恢复时才发现坏了）
tar -tzf ~/storage/shared/backup/prefix-$(date +%F).tar.gz | head -5
为什么环境快照也值得做 pkg upgrade 不会动 $HOME，所以业务数据本身是安全的。但环境崩了会连 bash 都起不来（CANNOT LINK EXECUTABLE "bash": library "libandroid-support.so" not found），那时你连命令都敲不了，“报错再修”这条路直接失效。

12.2 恢复（确认要回滚时才用）

执行前先确认三件事 ① 你要恢复到哪个包（选对文件名，别恢复到几天前的旧快照）；
② 目标位置是否会被覆盖（tar -x 会直接覆盖同名文件，不会问你）；
③ 有没有把当前状态也备份一份（万一恢复错了还能回去）。 
# ① 先列出备份包里的内容，确认它是你要的那个
tar -tzf ~/storage/shared/backup/prefix-2026-10-22.tar.gz | head -20

# ② 恢复业务数据（-x 解压 / -z gzip / -f 指定文件 / -p 保留原权限）
#    -C 指定解压到哪，这里解到家目录
tar -xzpf ~/storage/shared/backup/data-2026-10-22.tar.gz -C $HOME

# ③ 恢复运行环境（必须在 Failsafe 会话或已有可用 shell 的情况下执行）
tar -xzpf ~/storage/shared/backup/prefix-2026-10-22.tar.gz \
  -C /data/data/com.termux/files

# ④ 恢复后刷新包状态，修复可能的中断安装
dpkg --configure -a

# ⑤ 处理依赖不完整的情况
apt --fix-broken install

# ⑥ 验证环境是否可用
php -v | head -1
ls $PREFIX/bin/ | wc -l

12.3 环境崩到连命令都敲不了时

症状：打开 Termux 就报 CANNOT LINK EXECUTABLE "bash"，任何命令都不响应。

# 1. 长按 Termux 图标（或点通知栏），选择 "Failsafe" 会话
#    这是一个最小化 shell，不加载你的 .bashrc

# 2. 手动设置环境变量（Failsafe 里这些可能是空的）
export PREFIX=/data/data/com.termux/files/usr
export LD_LIBRARY_PATH=$PREFIX/lib
export PATH=$PREFIX/bin:$PATH

# 3. 确认能执行基本命令
ls $PREFIX/bin/bash

# 4. 在这个会话里解回快照
cd /data/data/com.termux/files
tar -xzpf ~/storage/shared/backup/prefix-2026-10-22.tar.gz

# 5. 退出 Termux 重新打开
如果 Failsafe 也救不回来 最后的选项是重装 Termux。注意：卸载 app 会删掉整个 ~/，所以数据备份必须在 /sdcard（共享存储）里。重装后先 termux-setup-storage，再把数据搬回来。
